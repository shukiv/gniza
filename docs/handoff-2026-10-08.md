## How the fleet is operated

**Channels.** .143, .53, .144 and .10 follow **dist**: `gh workflow run
release --ref master` builds the `dist` branch; the version is `git
describe --tags` of the built commit. .148 and .163 follow **Published
releases** and move only on a pushed `v*` tag. Ask the user before tagging.

**Install set.** After a release, install on .148, .143, .53, .144 and
.163 without asking. .10 waits for the user's word every time.

**Install, by hand, over the admin socket** (the scripts that did this lived
in a session scratchpad and are gone; this is what they did):

```sh
S=/var/run/gniza/admin/ui.sock
pgrep -x restic && exit 1                      # never during a run
T=$(curl -s --unix-socket $S "http://gniza/?p=accounts" \
    | sed -n 's/.*name="csrf" value="\([^"]*\)".*/\1/p' | head -1)
curl -s -o /dev/null --unix-socket $S --data-urlencode "csrf=$T" \
    "http://gniza/?p=settings/update/check"
curl -s -o /dev/null --unix-socket $S --data-urlencode "csrf=$T" \
    --data-urlencode "version=v0.3.15" --data-urlencode "confirm=1" \
    "http://gniza/?p=settings/update/install"
curl -s --unix-socket $S "http://gniza/?p=settings&tab=version" \
    | grep -o 'Version[^<]*'; systemctl is-active gniza
```

For a dist server, first wait until the gzip variant of
`https://raw.githubusercontent.com/shukiv/gniza/dist/SHA256SUMS` matches
the tarballs (the CDN serves the old build for 10+ minutes). Right after a
tag is published, the first check on a releases server may not offer it
yet; retry a minute later.

**Read-only health check.** Every page answers JSON with
`Accept: application/json`: `?p=logs` (backups), `?p=logs&tab=restores`
(rehearsals and restores), `?p=logs&tab=system`, `?p=destinations`
(lock, check, retention, census), `?p=` (overview sentence and concerns).
A `kind: not-rehearsed, status: cancelled` row is a rehearsal skipped for
room or time, retried after seven days; it is not a failure.

**Drills.** Only on a disposable account. cPanel refuses a domain under
`.invalid`; `.test` is accepted. `whmapi1 --input=json` and `uapi
--input=json` take their arguments as JSON on stdin, which keeps a password
out of `argv`; `whmapi1` prints log lines before its JSON. Baseline with
`sha256sum` over the home and `mysqldump --skip-comments --skip-dump-date`;
expect cPanel to rewrite `.htaccess` after creation and `restorepkg` to set
mail files to mode 640 — neither is a restore fault. Remove the account with
`/scripts/removeacct --force` (cPanel) or `CMD_API_SELECT_USERS` with
`confirmed=Confirm&delete=yes&select0=<user>` (DirectAdmin).

**.143's `/home/pager/application_backups`** is the tenant's own tool
writing ~1.5 GiB tarballs several times a day. Gniza has always excluded
it there; the disk pressure is the tenant's, not the backup's.

## Next issue: `cprest-88j` — the restore page's default backup

**What happened.** On .163 on 2026-10-04 a disposable account had three
snapshots. The first `restore/start` form on
`?p=restore&account=<u>&repository=<id>` carried `71bbf517`, the oldest —
the backup Gniza took the moment the account first appeared, before it held
anything. One `apply=1&confirm=1` later, cPanel restored it with `--force`
over the live account and reported success. The account was back to its
first night, silently.

**What the code says.** `internal/webui/handlers.go:3297-3306` sorts
`view.Snapshots` newest first by `Time`; `:3322` defaults `SnapshotID` to
`Snapshots[0]`; `internal/webui/templates/restore.html` ticks row index 0.
That should have been the newest. `internal/resticrun/restore.go:125`
(`rawSnapshots`) sorts ascending by `Time` before the engine sees the list,
and `engine.Snapshots` (`internal/node/node.go:~620`) returns what the
runner gives it. So the first thing to establish is what `Time` the page
received: if it is zero or equal across snapshots (a census-fed list, a
field dropped in JSON), the newest-first sort is a no-op and the runner's
oldest-first order leaks through as the default.

**Reproduce.** Any account with several snapshots: fetch the page over the
socket, read the hidden `snapshot` value and the ticked radio, compare with
`restic snapshots --json` for that account.

**Done means.** The ticked row is the newest; the whole-account confirmation
names the date of the backup it will put back (today it names only the
snapshot id — see `confirmWholeAccount` in `handlers.go`); a test in
`internal/webui` asserts the order with three snapshots of distinct times;
`docs/guide/restoring.md` loses the warning paragraph that points at this
bead.

## Rules that are easy to miss

- `.beads/` is never staged. Commit messages end with the session line and
  never carry `Co-Authored-By`.
- `rm` is not used; `trash` on the development machine, a move into
  `/root/.local/share/Trash/files/` on a server.
- Passwords and keys are never printed in chat or in a log line; a drill's
  password files live in a root-only directory and go to the trash with it.
- A whole-account drill on .148 shares its volume with the live account:
  state what it will consume and get a yes first.
