## What is uncommitted, and why it exists

Three weak spots an automated review found in v0.3.18, fixed in the working tree,
with `go test ./...`, the race detector on the upkeep tests, `make vet` and `make
vuln` all passing when last run:

- A schedule that fired and queued nothing, or a restart during the run, could stop
  the upkeep. `upkeepOverdue` replaces `scheduleFiredWithin`, and a job that never
  finishes no longer stops an overdue destination check.
- Retention did every repository in one go. It now does one per tick.
- A look for locks that timed out counted as done for twenty hours. Each repository
  now has its own time limit, and only a complete look counts.

Having one repository and at least one account rules out some of these on this
fleet, but not a restart during a run, a stuck job, or a timed-out look. None has
been seen to happen.

## Install, over the admin socket

The scripts for this live in session scratchpads and get wiped; this one was lost
again on 11-01. The token and version read below were tried on .66 on 11-01. Never
print the token, and refuse while a restic is running.

```sh
V=v0.3.19
S=/var/run/gniza/admin/ui.sock
pgrep -x restic && exit 1
T=$(curl -s --unix-socket "$S" "http://gniza/?p=accounts" \
    | sed -n 's/.*name="csrf" value="\([^"]*\)".*/\1/p' | head -1)
curl -s -o /dev/null --unix-socket "$S" --data-urlencode "csrf=$T" \
    "http://gniza/?p=settings/update/check"
curl -s -o /dev/null --unix-socket "$S" --data-urlencode "csrf=$T" \
    --data-urlencode "version=$V" --data-urlencode "confirm=1" \
    "http://gniza/?p=settings/update/install"
# after the restart:
curl -s --unix-socket "$S" -H 'Accept: application/json' \
    "http://gniza/?p=settings&tab=version" \
    | python3 -c 'import json,sys; print(json.load(sys.stdin)["data"]["Update"]["Running"])'
systemctl is-active gniza
```

Right after a tag is published, the first check on a releases server may not offer
it yet; retry a minute later. Dist servers need the gzip variant of
`https://raw.githubusercontent.com/shukiv/gniza/dist/SHA256SUMS` to match first,
because the CDN serves the old build for 10 minutes or more. A dist build reports
the tag name only if master HEAD carries the tag when it is dispatched.

The schedule page over the socket is `?p=schedule`, and answers JSON with
`schedule_cron`. Other read-only pages are in
[the previous handoff](handoff-2026-10-08.md#how-the-fleet-is-operated).
