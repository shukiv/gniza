# v0.2.6

## The issue arrives holding the report

**Report a problem** now opens the tracker's new-issue form with the whole
report in it, not only what you typed: versions, this server's recent
failures, its settings without credentials, and the service log. Type what
went wrong, press **File it**, read the issue GitHub shows you, press
GitHub's button.

[v0.2.5](v0.2.5.md) moved reporting to the tracker and filled in the subject
and the description. An issue that arrives saying only "the restore failed"
costs a maintainer the same three questions the report exists to answer,
while the answers sat in a file somebody had to notice, download and attach.

It works from the dialog in the rail as well as from the full page. Filing
after **Show me the report** files exactly what was reviewed, not freshly
gathered logs that may now say something else.

## What is cut, and why it is the oldest lines

A URL cannot hold every line of a service log: GitHub answers 414 above
about 8 KiB. So the report is cut down until the link fits — the longest
section first, and each one keeps the largest tail of itself that still
fits, because what matters is nearest the failure.

On a real report that leaves all four sections and about twenty lines of the
log. **Download it** still hands over the uncut report as a file; attach
that when the log matters.

## Settings hold settings

**Where bug reports go** is gone from Settings. It was a box that could not
be typed in, holding an address this build compiles in, on a page of things
that change what the server does. Reporting has nothing to configure, so it
has nothing on that page. The tracker is named on the report page, where
somebody filing a report is looking.

## Unchanged

Nothing is transmitted from the server on its own. What the link carries is
redacted the same way the preview is, and the reviewed report is still
signed and still expires after twenty minutes.
