# v0.2.7

## One database that will not dump no longer costs an account its backup

A live account with 47 databases had one corrupt table in one of them.
Staging returned on the first failed `mysqldump`, so from the moment that
table went bad the account got **no new backup at all** — not its home
directory, not the other 46 databases. Every run failed the same way, and
would have gone on failing for as long as the table stayed broken. One
table is not a reason to store nothing.

The backup now carries on. What it could not take is written down against
the run, named on the row, and in the notification, every time:

```
Not in this backup -- database thelittleprinced_fwpl1: cpanel: mysqldump
thelittleprinced_fwpl1: exit status 2: mysqldump: Couldn't execute
'SELECT * FROM `qssq_sbi_feed_caches`': Lost connection to MySQL server
during query (2013)
```

The subject line says it too — *Backed up thelittleprinced, without one
thing it could not take* — because nobody goes looking in a job detail for
a hole they were never told about.

## It is still not a complete account

A run with something missing is not a failure: it stored everything else,
and that is worth having. It is also not a complete copy, so it cannot
authorise deleting the account it is a backup of.
[Termination safety](../guide/accounts.md#termination-safety) refuses it,
the same as it refuses a run with exclusions in force.

## No quiet holes

Two things make the difference between carrying on and losing data
silently.

The dump that failed is **deleted** rather than left behind. An empty
`.sql` restores as a database with no tables and says nothing about it.

And a failure that is really the server going away is not treated as one
database's fault. Reading a corrupt table can abort MySQL; every dump
attempted while it restarts fails for an unrelated reason. Gniza waits for
the server to answer again and retries that database.

This was measured rather than assumed. cPanel's own `pkgacct`, run against
the same account, survived the crash, dumped **16 of 47** databases, lost
the other 31 to `Can't connect to local MySQL server`, and exited **0**
saying `pkgacct completed` — a 1.47 GB archive where it had itself
reported `mysqlsize is: 4915611017`. An archive that looks complete and is
missing two-thirds of the data is the worst failure a backup tool has.

## Also

A failed `mysqldump` has said what mysqldump said since
[v0.2.4](v0.2.4.md). That is what identified this table.
