# v0.3.0

## Gniza runs on DirectAdmin

The one-line installer now looks at the server it is on and installs the
package for the panel it finds:

    curl -fsSL https://github.com/shukiv/gniza/releases/latest/download/get.sh | sh

On a cPanel server that is what it always was. On a DirectAdmin server it
is Gniza's own plugin, under **Admin Tools**, with the same pages: what is
covered, where backups go, when they run, and what can be restored.

A release carries one package per panel and both are signed by the same
checksums file, so a DirectAdmin server verifies its download exactly the
way a cPanel server verifies its own. A server whose panel a release has
no package for is told so before anything is downloaded, rather than
installing a package meant for another panel.

## A DirectAdmin backup reads the account where it lies

DirectAdmin's own backup writes the whole account into one archive. Doing
that every night meant reading the account three and a half times and
writing it twice to store a few gigabytes of change — for accounts that
had not changed at all.

Gniza now asks DirectAdmin for the account's records without the
account's own files, and hands restic the home directory as a path. That
is the shape cPanel has always had, and it is what makes restic store
only what moved. On the validation host the nightly cost fell from 435
GiB read to the files that actually changed.

The mail is the exception: asking DirectAdmin for the mailboxes' own
passwords means asking for the messages too, so those are read once and
then dropped, because they are under the home directory already.

This is asked for one server at a time, with the agent's
`-directadmin-read-home-in-place`, and only after a restore drill on that
server. A server that was not asked keeps the shape it had.

## What that costs in disk, measured

A backup in this shape writes the messages and the database dumps and
nothing else, so that is what it now reserves room for. Reserving the
whole account refused backups a disk had plenty of room for: a 19.7 GiB
account whose backup writes 296.5 MiB was refused on a volume with 22 GiB
free.

The same estimate now asks what the *next* backup will do rather than
what the last one did. It did not agree with the run it was estimating,
so the first account after every agent restart was measured for a shape
it was never going to use — and if that account was large it was refused
before the run that would have settled the question.

## The overview answers "am I covered?"

The first page is no longer a list of parts. It says whether the server
is covered, what happened last night, what runs next and what is failing,
and it reconstructs a night's backups as one run rather than three
hundred rows. Each repository says what it holds and how much room is
left where it is stored.

## Restores that put back what they took

A dozen fixes to the archive path, each one a way a backup could have
come back wrong:

- A hard link is repacked as a link rather than as a second copy, so a
  linked Maildir does not restore at twice its size.
- A filename that is not valid UTF-8 survives the manifest.
- A database named twice in one restore is restored once.
- A mailbox named `.` is not every mailbox on the account.
- A rehearsal reads a database dump without holding all of it in memory,
  and now looks inside a whole-account snapshot instead of only checking
  that it arrived.
- A backup says so when it holds an account it cannot put back.

## Smaller things

- Removing a destination revokes the credentials only it held.
- A withdrawn retention approval stays withdrawn.
- An executable arrives by rename rather than being written over itself.
- A destination that has gone stops holding up every other one.
- A job longer than a minute can still say how it went.
- A panel with no `ssl=` line in its configuration is reached over plain
  HTTP, which is what DirectAdmin's own default means.
- Every page names the panel it is served on, and offers only the
  mechanisms that panel has.
