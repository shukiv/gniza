# v0.3.12

## A server without a panel: choose what to back up

The Accounts page on a server with no panel listed the directories under
`/var/www`, `/srv` and `/opt`, and on the first such server it met there
were none. The page is now called *What to back up*, with one tab per
kind and a table on each; every row ticked becomes a source of its own:

- **Folders.** The folders under the roots, unticked, and a field for
  any other. Each is backed up from where it lies.
- **MySQL** and **PostgreSQL.** Every database the client can see, with
  its size and its users -- MySQL's grantees, PostgreSQL's owner --
  all ticked by default, and a box in the header for the column. Each
  becomes `mysql-<name>` or `pg-<name>`, dumped on every run; the
  users' grants or the roles are kept beside the dump for reference.
- **Docker / Podman.** Every container under the stack its compose file
  makes, with a box on the stack; each ticked container becomes one
  source per volume and bind mount, with its description and compose
  file kept beside. The stack's folder and the engine's `/etc`
  directory are offered as the configuration.

A source can be removed at any time; the backups already taken stay.
The terminal has the same screen: `a` folders, `m` MySQL, `p`
PostgreSQL, `c` containers, `d` remove. The tabs say when a client or
an engine is not there, and that a database inside a running container
is not consistent when its volume is read.

Nothing is backed up until chosen: a plain server upgraded to this
release opens on the form. [ADR 0025](../adr/0025-what-to-back-up-on-a-server-without-a-panel.md)
has the reasoning; the [plain-server guide](../guide/plain-server.md)
has the how.

## The schedule form is where what to back up is chosen

The same tables sit in the schedule form, under *What to back up*,
where a panel server's form asks which accounts. Two choices above
them: *everything on the list*, which covers every source now and any
chosen later, or *only what I tick below*. A row already on the list is
ticked by its name; a fresh row ticked goes on the list when the
schedule is saved, and is covered. So on a new server the first
schedule is the whole setup: tick the databases, the folders and the
stacks, save. A schedule that would cover nothing is refused rather
than saved empty. The schedules table says *Everything chosen* and
counts sources on such a server, and the copy under the form no longer
talks about mail and EasyApache there.

## The schedule page says the recovery key comes first

A schedule for a destination whose recovery key is still only on this
server is refused, which is right; but the refusal landed as a message
on the destinations page, so the form read as not working and bouncing
there. The schedule page and the terminal's schedules screen now say,
above the form, which destination's key has to be taken off first and
where that is done.

## The installer installs bzip2 itself

restic is published as a `.bz2`, and a fresh Debian has nothing that
reads one. The installer stopped with the `apt-get install -y bzip2`
line for the operator to run; it runs it now, with `dnf`, `yum` or
`apt-get`, without asking, and stops only if that did not work.

## Under it

`panel.Chooser` is the optional interface a provider implements when
its accounts are chosen rather than listed; cPanel and DirectAdmin do
not, and their pages are as they were. What there is to choose from is
read when the form is asked for, not on every refresh of the list. The
folder typed in by hand posts `folder_path` and `folder_name` now,
since the schedule form has a `name` of its own. The empty accounts page no longer
names `/var/cpanel/users` on a DirectAdmin server. A PostgreSQL dump is
`<name>.pg.sql`, and the provider loads it with `psql` from the name
alone.
