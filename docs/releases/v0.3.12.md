# v0.3.12

## A server without a panel: choose what to back up

The Accounts page on a server with no panel listed the directories under
`/var/www`, `/srv` and `/opt`, and on the first such server it met there
were none. The choosing is in the schedule form now, one tab per kind
and a table on each; every row ticked becomes a source of its own, and
the page lists them as *Sources*:

- **Folders.** The server's directories as a tree from `/`, with the
  usual places a click away and a path bar: open a folder to look
  inside (its files are shown, greyed), tick it to back it up. A folder
  already backed up, or inside one that is, says so and cannot be ticked
  again. A folder can also be named by hand. Each is backed up from
  where it lies.
- **MySQL** and **PostgreSQL.** Every database the client can see, with
  its size and who has rights on it -- each MySQL user with its
  privileges, PostgreSQL's owner -- all ticked by default, and a box in
  the header for the column. Each becomes `mysql-<name>` or
  `pg-<name>`, dumped on every run. Beside the databases on each tab,
  every database user or role the server has, with what authenticates
  it and what it can reach, ticked by default too and with a box in
  that header; a user ticked is kept with the sources that dump its
  databases, password hash and grants, so a restore brings the login
  back. A PostgreSQL role is made again before the dump is loaded: a
  plain dump names the role that owns its tables, and a restore onto a
  server without it used to stop at the first of them. Every user's
  grants and every role are also kept beside the record, for reference.
- **Docker / Podman.** Every container under the stack its compose file
  makes, with a box on the stack; each ticked container becomes one
  source per volume and bind mount, with its description and compose
  file kept beside. The stack's folder and the engine's `/etc`
  directory are offered as the configuration.

A source can be removed at any time from the Sources page; the backups
already taken stay. The terminal chooses on its Sources screen: `a`
folders, `m` MySQL, `p` PostgreSQL, `c` containers, `d` remove. The tabs say when a client or
an engine is not there, and that a database inside a running container
is not consistent when its volume is read.

Nothing is backed up until chosen: a plain server upgraded to this
release says so on its Sources page and in the schedule form. [ADR 0025](../adr/0025-what-to-back-up-on-a-server-without-a-panel.md)
has the reasoning; the [plain-server guide](../guide/plain-server.md)
has the how.

## The schedule form is where what to back up is chosen

The same tables sit in the schedule form where a panel server's form
asks which accounts, and what is ticked is what the schedule covers. A
row already on the list is ticked by its name; a fresh row ticked goes
on the list when the schedule is saved, and is covered. Every source
ticked means everything, now and later, the schedule *Back up all*
runs; leave one out and it covers only what is ticked. So on a new
server the first schedule is the whole setup: tick the databases, the
folders and the stacks, save. A schedule that would cover nothing is
refused rather than saved empty. The schedules table says *Everything chosen* and
counts sources on such a server, the overview counts sources too, and the copy under the form no longer
talks about mail and EasyApache there.

## The schedule page says the recovery key comes first

A schedule for a destination whose recovery key is still only on this
server is refused, which is right; but the refusal landed as a message
on the destinations page, so the form read as not working and bouncing
there. The schedule page and the terminal's schedules screen now say,
above the form, which destination's key has to be taken off first and
where that is done.

## An SFTP destination logs in with a password or a key

The form for another Linux server asks how the backups log in. *The
user's password* is kept encrypted on this server and used at every
backup: adding the destination proves it opens a login and makes the
directory first, and a wrong one is refused in words. *A key Gniza
makes* is what there was: the public half goes into the user's
`authorized_keys`, by you or by Gniza given the password once. Before,
the password field was optional and did only that second thing, and the
page that asks you to agree to the server's host key came back without
the password in it, so a destination was saved as one whose key you
would install by hand while you believed the password had been used.
The host key now comes up as a dialog over the form, with the
fingerprint, the password field again where one was typed, and a button
to agree; a post without the password is not taken as a login without
one. An existing destination
can be edited to a password; its card and its recovery card then stop
showing the key it no longer uses. The terminal gets the same choice.
[ADR 0026](../adr/0026-an-sftp-destination-logs-in-with-a-password-or-a-key.md)
says how the password reaches ssh.

## Test on an SFTP destination logs in

Test used to prove only that the port answered, then say "Reachable" and
hand restic's complaint over when creating the repository failed:
"subprocess ssh: Permission denied (publickey,password)" and three more
lines. It now opens the sftp subsystem the way restic will, and says in
words what stood in the way: the server does not accept Gniza's key for
that user, so put the public key from the destination's card into that
user's `authorized_keys`; or the host key is not the one pinned when the
destination was added; or the account has no sftp subsystem.

## A server without a panel upgrades itself

The self-upgrade unpacked the plain package and then ran nothing: the
script the transient unit runs looked for the cPanel and DirectAdmin
trees only, and recorded "the release left no installer here". It looks
for `gniza-plain` too now.

## uninstall.sh --everything leaves nothing behind

An uninstall moves what it takes off the server aside and keeps the
master key, the state database and restic's cache, so a reinstall comes
back where it was. `sh /usr/local/share/gniza/uninstall.sh --everything`
deletes those too, with restic and what was moved aside: nothing of
Gniza is left. It asks for the phrase `delete everything` on the
terminal before anything is stopped, because without the master key the
recovery key written down is the only way into the backups; `--yes`
answers for a script. The backups at the destinations are never touched.
Every installer's uninstaller takes the flag, and an option it does not
know is refused rather than taken for a plain uninstall.

## The installer installs bzip2 itself

restic is published as a `.bz2`, and a fresh Debian has nothing that
reads one. The installer stopped with the `apt-get install -y bzip2`
line for the operator to run; it runs it now, with `dnf`, `yum` or
`apt-get`, without asking, and stops only if that did not work.

## Logs: search, more detail, and a way to clear them

The Logs page has a search box that reads all of the history rather than the
rows a tab shows: any words on a row — account, schedule, date, destination,
snapshot id, database, path, result, or what went wrong — and the tabs carry
the search and count what matches. The service log gained **Containing**.

A backup row says what it backed up, under which schedule and how long it
took, and **Details** (it was **Report**, and only restic's words) says when
the run was queued, started and finished, the paths and databases, what the
schedule left out, and for each copy the destination and where it is, the full
snapshot id, bytes read and new, the files restic counted and how long the
upload took. What a run backed up and the file counts are recorded from this
release on; older rows say so.

**Clear logs…** removes backups, system backups, restores and account events
from the history, as ticked. It keeps what is more than a log — the last run
and the last good copy of each account at each destination, which the overview
and termination safety read; the last rehearsal; a download still waiting;
anything running — and a snapshot's "some files unreadable" mark outlives the
run that made it. Snapshots are not touched. See the [Logs guide](../guide/logs.md).

## Restoring one part of a large account fits again

A restore of one database, one mailbox or a few files is given room for that
part. It was sized that way once already, and then measured again against the
whole backup a step later, so a restore of one item out of a 48.7 GiB account
asked for 176.5 GiB and was refused.

## A DirectAdmin restore no longer stops at a file somebody else owns

DirectAdmin unpacks an account's files as the account, and stops at the first
one that belongs to anybody else. On one server 66 of 144 accounts had such a
file, and the backup of each said every night that a restore of it would stop
there. The archive rebuilt for a restore now names the account as the owner of
all of its own files, the restore finishes, and the warning says what happens
instead: the files come back as the account's. See the
[DirectAdmin guide](../guide/directadmin.md#files-in-a-home-that-belong-to-somebody-else).

## A DirectAdmin server's own configuration is backed up

**Also back up the server's own settings** did nothing on DirectAdmin but
fail: the system backup was a refusal, every night, on every DirectAdmin
server. It now stores DirectAdmin's `conf/` and `data/admin`, what CustomBuild
was told to build, the mail, DNS, web server, PHP, MySQL and FTP
configuration, the DNSSEC signing keys, the system users and root's cron,
with a manifest of what was copied and what this server does not have.

Nothing puts it back. The files are browsed and downloaded from **Restore**
under `@system`, and a replacement server is set up from them by hand. See the
[DirectAdmin guide](../guide/directadmin.md#the-servers-own-configuration) and
ADR 0019.

## The overview says what is wrong with the server itself

The first line of the overview counts accounts, and every account can be
covered while the server's own configuration has failed to back up every
night, or while a repository is locked or did not pass its check. Those are
listed under the first line now, each with the way to where it is dealt with,
and they colour it: a repository that did not pass is red, the others amber.

## Repositories are read back every week

Nothing had ever asked restic whether a repository could be read: *Checked* on
a destination was a login to it. It is called **Reached** now, and
**Integrity** beside it is `restic check` with a tenth of the stored data read
back, run for each repository once a week when nothing is due for four hours,
and at once with **Check now**. What is queued meanwhile waits for it. A
repository that does not pass says what restic found, and a new notification,
*A repository failed its integrity check*, is sent once. See the
[Destinations guide](../guide/destinations.md).

## A lock left by a killed backup no longer stops retention for ever

A backup that is stopped part-way — a reboot, the kernel, an operator —
leaves its lock on the repository, and restic never removes another
process's lock. Backups carry on past it, which is why nobody notices; a
retention plan, a prune and a check cannot. One server had carried such a
lock for nineteen days and grown to 5908 copies with retention failing every
night.

Retention now looks at the locks when it is refused by one. Those nothing
holds — not refreshed for half an hour, or taken on this server by a process
that no longer exists, which is restic's own rule — are removed by
`restic unlock`, and the plan is taken again. Nothing is removed while this
server has a backup or a restore running, and a lock that may still be held
is left where it is and named on the page. **Remove stale locks** on the
Destinations page does the same by hand, and every repository is looked at
once an hour while the server is idle.

Where they came from is fixed too: a restic that Gniza stops — a timeout, a
cancelled run, the service going down — was killed outright, which gave it no
chance to remove its lock. It is asked to stop first, and killed only if it
has not ten seconds later.

A plan older than the last failure is not offered for approval any more: it
describes the repository as it was before it stopped answering. And what is
kept at a destination is shown for every destination with a repository, not
only for one that logs in with a key.

## A DirectAdmin restore needs room for two copies, not three

A restore or a rehearsal on DirectAdmin was given room for the account
three times over, because three copies were on the disk at once. An account
of 17 GB was refused with 42 GB free.

The rebuild now lets go of each file as soon as it is in the archive, so two
copies are the most it holds, and two is what it asks for. Nothing about the
archive DirectAdmin is handed has changed.

## Restores can be rebuilt on another volume

A restore was rebuilt in the staging directory, and staging cannot move: its
path is recorded in every backup. On a server where staging is on `/` with
7 GB free and `/home` has 38, that meant four accounts could not be restored
whole or rehearsed at all, with room for every one of them a directory away.

Settings → Storage has **Where restores are rebuilt**. Name a directory on
the larger volume and restores, rehearsals and rebuilt archives go there;
backups still stage where they always did. The directory must be out of
every account's reach — root's all the way down, writable by nobody else —
and one that is not is refused with the name of the directory that is open.
It cannot be changed under a running job, or while restored files wait in
the directory being left.

## Under it

`panel.Chooser` is the optional interface a provider implements when
its accounts are chosen rather than listed; cPanel and DirectAdmin do
not, and their pages are as they were. What there is to choose from is
read when the form is asked for, not on every refresh of the list. The
folder typed in by hand posts `folder_path` and `folder_name` now,
since the schedule form has a `name` of its own. The empty accounts page no longer
names `/var/cpanel/users` on a DirectAdmin server. A PostgreSQL dump is
`<name>.pg.sql`, and the provider loads it with `psql` from the name
alone.
