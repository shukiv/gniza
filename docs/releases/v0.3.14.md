# v0.3.14

## A whole-account restore on cPanel works again

A restore that puts an account back over the live one rebuilds the account as
a directory and hands that directory to cPanel's `restorepkg`, which takes one.
Gniza's own check in front of `restorepkg` still refused anything but a file,
so every such restore of a backup stored as a tree failed with *restore
archive … is a directory*, before cPanel was asked anything. Restores left on
the server to collect, restores of single files and databases, and rehearsals
were not affected, which is how it went unseen: it was found by restoring a
disposable account on a live server.

The directory is now handed over.

## A destination is not removed while its recovery key is only on the server

Removing a destination revokes the password of its repository. Where that
password had never been saved anywhere else, removing the destination left
every backup stored there unreadable for good, and said only that Gniza *no
longer knows how to read it*.

A destination that holds backups is now refused removal until its recovery key
has been noted as saved: press **Recovery key**, keep it somewhere else,
confirm, then remove. A destination whose repository was never created has
nothing to lose and is removed as before.

## A killed database restore leaves no password file behind

A database is restored through a login made for that one import, with its
password in a file in the temporary directory. Both are taken away when the
import ends; an import that was killed took away neither.

At startup Gniza now removes those files. A login left behind is named in the
log and not dropped — that changes the live database server, and is the
operator's to do. With the file gone, nothing on the server knows its password.
