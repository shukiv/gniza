# v0.3.16

## A DirectAdmin customer has a page of their own

**Gniza Backups** in a customer's DirectAdmin now shows their own restore
points and hands them any part of one -- or the whole account -- as a
copy: the same page cPanel accounts have had since v0.2, reached the way
DirectAdmin reaches a plugin.

Who is let in is decided the way it is on cPanel, with DirectAdmin's own
means. The page runs as the account, so the socket knows which account
is asking; the plugin carries the customer's DirectAdmin session, and
Gniza puts it to DirectAdmin on every request and requires the answer to
name that account. A cron job or a site running as the account has no
session to carry and is refused. A host using login-as reaches the page
as the customer.

DirectAdmin wraps everything a plugin prints in its skin, so the copy
cannot reach the browser through the page. It is written into the
customer's home directory instead, under `gniza-downloads`, as the
account -- root reads the archive the account cannot, the account writes
the file -- and the page shows it and opens the File Manager on it. The
copy goes when the restore's output does, after **Keep restored files
for** days, removed by the account as well.

One thing the cPanel page does is not offered here, and the page says so
by not offering it: nothing is put back into the live account. The
DirectAdmin provider's put-backs are not built yet, and a button that
reached one would reach a refusal.

Whether a host's customers see the page at all is the **self-service**
setting on the Settings page, off until a host turns it on, for every
account or for named packages. On cPanel the Feature Manager decides, as
before.

## The account socket asks the panel who its accounts are

The account-facing socket used to read cPanel's own files to decide
whether the uid on the other end is an account, and whether it is
suspended. It now asks the panel, which is what lets the same socket
serve DirectAdmin accounts. Nothing changes for a cPanel server.
