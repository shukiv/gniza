# v0.3.17

## A schedule runs once a night

On a server one or two hours ahead of UTC, a daily schedule ran twice every
night: a schedule set for 02:00 also ran at 03:00 or 04:00. A cron line has no
zone and is read in the zone of the time it is handed, and the last firing comes
back from the store in UTC, so inside the two-hour catch-up window the schedule
also came due at 02:00 UTC. Nothing failed: the second run was another good
backup, with its load and its snapshots. Israel in winter is one of those zones,
and the five servers it was found on ran twice from the night the clocks went
back.

A schedule is now read on the server's own clock. The hour the clocks go back
also happens twice, and a schedule set inside it used to run in both; the second
time is passed over, so it runs once. A schedule that runs every few minutes
waits out that hour rather than running through it, once a year.

## The agent outlives a journald restart

The agent's log is a socket to journald, and cPanel's nightly update restarts
journald. The next line the agent wrote then killed it with SIGPIPE, which
systemd reports as a clean exit: `gniza.service: Deactivated successfully`, and
a new agent fifteen seconds later. It happened several times a month on each
cPanel server, often at the moment a schedule fired, because that is the next
thing an idle agent says. It also stopped a v0.3.16 upgrade on two servers as it
started, which is why they stayed on v0.3.15. A backup running at that moment
would have been lost with it.

A broken log is now only a failed write. The agent connects back to journald
and carries on, so `journalctl -u gniza` keeps working without a restart, and
stderr and stdout both go to the new connection, so a stack trace reaches the
journal too.

## Smaller things

The rail's documentation button opens the documentation on gniza.app, and the
guides include one for cPanel, which had none of its own.

The binaries are built with Go 1.26.10, which carries the standard library's
fix for GO-2026-6809 in `crypto/x509`.
