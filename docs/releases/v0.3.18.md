# v0.3.18

## Upkeep happens around the backup, not on timers

A server logged in to its destination about eighty times a day, and only two of
those were the backup. The destination check and the look for stale locks each
ran every hour, the count of what a repository holds every six, and retention
whenever twenty hours had passed, whatever else the server was doing. A login
alert on the backup server arrived every hour for a backup that takes seconds.

The upkeep now belongs to the schedule. Just before a schedule queues its
backups, the repositories are looked at for stale locks, because a lock left by
a killed prune or check would stop every one of them. Once the last backup has
finished, the destination is checked, retention runs, what is left is counted,
and an integrity check runs if one is due. That is about eight logins a day, all
around the backup. Each task runs at most once in twenty hours, so a schedule
that fires every hour does not bring the hourly logins back.

A server with no schedule firing has nothing to follow, so after thirty hours it
does the same upkeep by itself, about once a day.

What this gives up: a destination that goes away is noticed at the next backup
rather than within the hour, and the free space and the counts on the page can
be up to a day old. The page now shows a reading's date after thirty-six hours
rather than eighteen.

## A correction to the v0.3.17 note

That note said a schedule ran twice every night on a server one or two hours
ahead of UTC. It did not always: whether the second run fired came down to a
fraction of a second in the scheduler's timing, so some servers ran twice every
night and others only on some nights.
