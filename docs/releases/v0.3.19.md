# v0.3.19

## Upkeep no longer depends on a schedule having fired

v0.3.18 moved the upkeep to around the backup, and a review of it found ways the
upkeep could fail to happen or get in the way.

A schedule that fired every night and queued nothing, because it found no
accounts, or a restart during the run, left the upkeep with nothing to follow,
and a server in that state could go without it indefinitely. What starts the
upkeep now is the readings themselves: if a destination check or a repository
count is more than thirty hours old, the upkeep runs whether or not a schedule
has fired.

A job that never finishes held all of the upkeep back, including the check that
would show the destination had gone. An overdue destination check now runs
beside a running job, because it does not touch the repository. Everything that
does still waits.

Retention ran every repository in one go, so a backup due meanwhile waited behind
all of them. It now does one repository each time the scheduler comes round, and
what is queued runs in between.

A look for stale locks that timed out counted as done, so the next one was most
of a day away, and on a server with several repositories one slow destination
used up the time for the others. Each repository now has a time of its own, and
a look that did not reach all of them is tried again when the next schedule
fires.
