# v0.3.2

## A DirectAdmin backup stops storing what nobody asked it to keep

Three kinds of directory were being read, compressed, hashed and uploaded
every night, and none of them holds anything a restore needs.

**The file manager's trash.** Files the customer deleted. On one
validation host that was 1.3 GiB of a 20 GiB account, and 4.2 GiB across
a host of 142.

Deleted files also stop restores. DirectAdmin unpacks the home archive as
the account, so a file in it owned by root fails on the first attempt to
set its times and takes the rest of the restore down. Three of the four
root-owned files under one account were in its trash — putting files the
customer threw away between them and the files they kept.

**The backups applications write into a site.** Installatron and
Softaculous write a compressed copy of the site and a dump of its
database on every automatic update; Akeeba and BackupBuddy do the same
inside the site itself. Each one is a fresh compression, so it
deduplicates against nothing, and what it holds is what the snapshot
already holds directly. `application_backups` alone is on 77 of one
host's 142 accounts.

**Caches that are rebuilt on demand.** WordPress's page, widget and
captcha caches, Smarty's compiled templates, and the ephemeral halves of
Magento's `var/`. On the same host WordPress's cache was 4.90 GiB across
85 sites.

And Apache's per-directory `error_log`, which grows without a bound until
somebody notices: 1,069 of them, 1.45 GiB.

Together that is about a twentieth of everything under management on that
server, read and hashed every night to store caches and error logs.

## What is deliberately still stored

The list names places, never file types. A customer's own `.zip`, `.sql`
or `.tar.gz` is stored, because leaving out a cache costs a slow first
page load and leaving out their files loses them. `var/` is left out at
the four names Magento uses for ephemeral data rather than whole, for the
same reason — a site can keep its own files there.

What each pattern does was settled by running restic over a tree holding
both the caches and the files that look like them, and checking what came
back.
