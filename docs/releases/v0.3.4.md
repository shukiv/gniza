# v0.3.4

## A backup refused for room it did not need

A backup on a new server stopped with:

    not enough room to stage this account: it needs 57.2 GiB free and
    there is 16.5 GiB

for an account whose backup would have written megabytes.

Measuring an account meant walking its whole home directory and counting
every byte, including the directories DirectAdmin's own backup skips —
`backups`, `user_backups`, `admin_backups`. Nothing in those reaches an
archive DirectAdmin writes, so nothing in them is in a Gniza backup
either, and they are where the bulk of an account often is. On one
validation server the administrator's home was 6,737,318,299 bytes, of
which 6,732,830,003 was `admin_backups`: 99.93% of the number that
decided whether the backup fit.

They are not counted now, and the walk no longer descends into them,
which is the difference between reading 6.7 GB of archives every night
and not.

What Gniza leaves out on top of DirectAdmin's own list — the application
backups, the trash, the caches — is still counted, because DirectAdmin
does put those in the archive it writes and a server that stages the
whole archive has to hold them.

## The installer's closing warning

It was the last of eight lines printed in the same voice as the progress
above it, so it read as more progress. It is a ruled, highlighted block
now, coloured only when the output is a terminal.

The words were also wrong. It said the DirectAdmin provider "backs up a
whole account as one archive", which stopped being true when split mode
landed — nobody noticed, because it was a second hand-written copy of a
sentence the agent already prints. There is one text now, and a test that
fails if the two drift apart again.

## A note that named a column the table did not have

The backups table's footnote explained "New" for every release after that
column was renamed to "Stored".
