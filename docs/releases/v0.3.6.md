# v0.3.6

## A server without a panel

Gniza installs on a server that has no cPanel and no DirectAdmin: a
LAMP box, a docker or podman host. The same one-liner finds neither
panel directory and takes the plain package (ADR 0022).

An account is a directory directly under one of the roots in
`/etc/gniza/plain.env`, `/var/www`, `/srv` and `/opt` by default. A
MySQL database named after the account, alone or with an underscore and
a suffix, is backed up with it. The files are read where they lie; the
dumps and a record of what was taken sit beside them in every backup.
The system backup takes the web, PHP, database, container, cron and
SSH configuration, the certificates, the unit files, and a manifest of
the installed packages and of the containers and volumes present.

Docker and podman named volumes are not found on their own yet. Until
they are, adding `/var/lib/docker/volumes` to the roots makes each
volume an account.

## A terminal interface

There is no page to open on such a server, so the interface is a
terminal one:

```bash
gniza-agent -tui
```

It reads the same pages the plugins draw, as data, over the same
socket, and posts the same forms. Destinations are added, an sftp
host key is agreed to before anything is sent, the recovery key is
shown when the destination is ready and noted once written down;
schedules are added, edited, run now and removed; an account is backed
up now; the logs are the five tabs the plugins have. The Restore and
Settings screens show what there is. Asking for a restore or changing
a setting from the terminal is not written yet; the guide keeps the
`curl` forms for that, and for scripts.

Any page answers as data when asked with `Accept: application/json`.
That is what the terminal reads, and what a script can.

Restore of files and databases on a plain server is written and not
yet proved on a live one; the provider says so at start.

## A destination that failed with "repository does not exist"

Every repository after the first copies its chunker parameters from
the first. Two things left a destination with no repository at all,
and every backup to it failing with restic's `repository does not
exist`: the source could not be opened in the same restic process (two
sftp destinations with keys of their own disagree about `sftp.args`,
and restic applies `-o` globally), or the source had been removed. In
both cases the repository is now created with parameters of its own,
and the log says why.

## DirectAdmin

- A DirectAdmin account is read where it lies by default. The restore
  drill proved the rebuilt archive on two servers, which is the
  condition ADR 0021 set. `-directadmin-stage-whole-archive` keeps the
  old shape for a server that wants it.
- An account the server no longer has is restored, not refused:
  DirectAdmin creates it from the archive, as its own restore does. The
  restore of a deleted account on the validation host found and fixed
  three more things on the way: the created account could not reach
  the archive, DirectAdmin generated the zone file under the service's
  umask and named could not read it, and a finished task lost its
  post-hooks.
- A page served through DirectAdmin's Evolution skin fetches itself by
  the plugin address, so the live regions keep current. The Version
  card used to say a release was downloading for as long as it was
  open.
- The Remove button on DirectAdmin looked for the uninstaller where the
  WHM installer puts it, and always said Gniza was installed some other
  way.

## Publishing without a version

A release run started by hand publishes the signed build to the `dist`
branch, so a server that follows that channel in Settings installs it
without a version being cut.
